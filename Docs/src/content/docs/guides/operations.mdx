`INSTALLATION.txt` in the settings folder holds the exact commands for your project. Every command must address the saved project and settings folder explicitly: an unqualified `docker compose` from the source checkout can address a different stack.

## Address the correct installation

Replace both values with your actual settings path and the `ProjectName` recorded in `alexandria-config.json`. This Bash helper quotes paths containing spaces and passes each Compose argument separately:

```bash
alexandria_target='/srv/Alexandria settings'
alexandria_project='replace-with-saved-project-name'

alexandria_compose() {
  docker compose \
    --project-name "$alexandria_project" \
    --project-directory "$alexandria_target" \
    --env-file "$alexandria_target/.env" \
    --file "$alexandria_target/docker-compose.yml" "$@"
}
```

Do not source `.env` as a shell script or print resolved Compose configuration, which contains credentials. Validate without printing values:

```bash
alexandria_compose config --quiet
alexandria_compose ps --all
```

## Stop, start and inspect

```bash
# Stop this project's services while keeping containers and volumes.
alexandria_compose stop

# Start the saved stack using existing images, without building or pulling.
alexandria_compose up -d --no-build --pull never

# Inspect all states, including completed setup jobs.
alexandria_compose ps --all

# Follow recent logs, or look at one service.
alexandria_compose logs -f --tail 100
alexandria_compose logs --tail 200 api
```

`garage-init` and `rabbitmq-config` are setup jobs and should exit successfully. Every other selected service must be running, and services with healthchecks must become healthy. Confirm the HTTPS address and sign-in after starting.

<Aside type="caution">
  Use `stop` for routine downtime. `docker compose down` with the same explicit arguments removes containers and networks but normally keeps named volumes. **`down -v` deletes your data.** Never use volume pruning or delete the settings folder as a repair technique.
</Aside>

## Repair and change features

Run Builder again, select the existing settings folder and its source checkout, and review the recovered project, volume names, source path, features, address and certificate before deploying. Established credentials and data stay authoritative, and the installer stops if it cannot safely match legacy settings to Docker resources or a required volume is missing.

- **Retry** on a failure screen revalidates the environment and ownership and keeps verified preparation from that session. After an exit or cancellation, rerun with the same folder to resume.
- Services that already started keep running after a failure, and cancelling stops installer work without tearing the stack down.
- Repair does not reset an established administrator password, change an existing Garage capacity, or restore missing data. Restore a [backup](/operations/backup-and-restore/) for that.
- Builder is not an upgrade rollback manager and cannot downgrade the database schema. Take a backup before changing source or image versions.

To move an installation to another folder, follow the relocation procedure in `scripts/installer/README.md` in the source checkout.

## Installer failures

| Failure | What to inspect and do |
| --- | --- |
| Settings permission or log creation failure | Check ownership and write access to the settings folder and its parents. Deployment has not started if the installer cannot create its log. Do not switch users and generate a second identity in another folder. |
| Docker unavailable or permission denied | Check `docker info`, your account's Docker access and `docker context ls`. Remote SSH or TCP contexts are unsupported. |
| Missing source asset or template | Restore the complete matching source checkout, including `Templates/Local`. A moved source folder also breaks runtime bind mounts. |
| Busy HTTPS port | Choose a free port under network access. A port used by another project is not adopted. |
| Image build or dependency failure | Read the **installer log** in `installer-logs/` and the build output, since containers may not exist yet. Fix the named registry, network, disk, memory or compiler error and retry with the same folder. Do not replace `.env` or delete volumes. |
| Missing or corrupt audio model | Supply the model files, choose HTTPS downloads in the Audio models step, or switch analysis off. |
| Storage or messaging init failure | Inspect `garage`, `garage-init`, `rabbitmq-config` and `rabbitmq` with `ps --all` and their logs, fix the named error, then resume. |
| Docker address pools exhausted | Docker cannot create another project network. Remove only networks that belong to finished disposable tests and retry. Changing daemon address pools is a host decision. |
| Missing volume, ownership or ambiguous legacy identity | Stop and compare the saved project and volume names with Docker and your backups. A different project name creates an empty stack instead of recovering data. |
| Service unhealthy, stopped or duplicated | Inspect that service with `ps --all` and its logs. Disabled optional workers are not required. |
| Fresh admin check fails | Setup is incomplete even if the login page loads. Inspect API startup and authentication logs, then retry. |
| TLS warning or client connection failure | Follow `nginx/CLIENT-TRUST.txt`, and compare fingerprint, host or IP, expiry and client trust. Check LAN reachability, DNS and firewall. |

### Storage keys missing after init

If storage initialization succeeded but the credential handoff and the persisted keys in `.env` are both missing, reuse the existing project and volumes:

```bash
GARAGE_FORCE_CREDENTIAL_EXPORT=true alexandria_compose up -d --no-deps --force-recreate \
  --no-build --pull never garage-init
alexandria_compose ps --all garage-init
alexandria_compose logs --tail 200 garage-init
```

Wait for `garage-init` to exit 0, then rerun Builder with the same settings folder so it validates and saves the keys. The flag applies only to this command. Never paste the contents of `init-output/garage-credentials.env` into a support conversation.

## Logs, secrets and certificates

- Installer logs are timestamped under `installer-logs/` and readable only by their owner. Secrets are redacted, but review a log before sharing it. Avoid sharing `.env`, private keys, raw Docker inspect output or resolved Compose configuration.
- For generated certificates, rerun Builder in the last 30 days before the server certificate expires to renew it under the same local CA. For imported certificates, renew with the issuer and supply the new PEM certificate and its unencrypted private key. A lost local CA or a new self-signed identity means every client must trust the new certificate.
- Optional monitoring uses a privileged cAdvisor with read-only host mounts, including `/var/lib/docker`, and Alloy with access to the Docker socket. A read-only socket mount does not limit Docker API authority, so keep that host under your control.
