Alexandria is a solo-driven pre-alpha project that welcomes feedback and contributions. This page collects the conventions the codebase already follows so changes fit in.

## Ground Rules

- **Pre-alpha reality**: breaking changes are expected; nothing here is stable API yet
- **AGPL-3.0** — contributions land under the same license
- AI-assisted code is fine (the project itself uses it for tests/CSS) but you own what you submit

## Backend Conventions

| Area | Convention |
|---|---|
| Language | C# / .NET 10, central package management via `Directory.Packages.props` |
| Analyzers | SonarAnalyzer wired into every project through `Directory.Build.props`; treat warnings seriously |
| Static analysis | Qodana config in `Backend/qodana.yaml` |
| Architecture | Layered projects (see [Project Structure](/development/project-structure/)); dependencies point inward; Common has zero package deps |
| Endpoints | One FastEndpoints class per file under `Features/<Area>/`, validators alongside |
| EF | Fluent configurations per aggregate in `Alexandria.Data/Configurations/`; migrations via the design-time factory ([workflow](/development/database/#migrations-workflow)) |
| Logging | `LoggerMessage` source-generated partials (`*.Logs.cs` pattern), Serilog structured output |
| Tests | Unit + integration per [Testing](/development/testing/); new logic ships with tests |

Raw SQL is used deliberately where Postgres-specific features are needed — always `SqlInterpolated`, never `FromSqlRaw`.

## Frontend Conventions

The authoritative guide is `skills/ui-skill.md` at the repo root; the short version:

- **oxlint + oxfmt** gate everything: `pnpm lint`, `pnpm fmt:check` must pass
  - correctness/suspicious = errors, pedantic/style = warnings
  - files ≤500 lines, functions ≤100 lines, no `console`/`debugger`
- Nuxt UI v4 components over hand-rolled primitives; Tailwind v4 tokens with WCAG-AA contrast
- 8px spacing grid; `const name = () => {}` function style; no nested ternaries; empty states everywhere
- Data access through `queries/` + `mutations/` (@pinia/colada); Zod schemas validate API responses
- Type-checking is part of build: `pnpm build` fails on type errors

## Commits & PRs

Commit messages follow Conventional Commits style as practiced in the log:

```
feat: add admin audio analysis pages
chore: clean up old unused rabbitMQ init scripts
fix(docs): correct sidebar slug
```

Lowercase type prefixes (`feat`, `chore`, `fix`, `style`, `docs`), imperative summary, scope optional. PRs should state intent and note any schema/config migrations.

## Documentation

User/operator docs and developer docs live together in `Docs/` (Astro Starlight):

```bash
cd Docs && pnpm install && pnpm dev   # local preview
pnpm build                             # must pass before merging docs changes
```

New developer pages go under `src/content/docs/development/` and get picked up by the autogenerated sidebar. Pages carry a "verified against" footer listing checked sources — keep claims verifiable.
