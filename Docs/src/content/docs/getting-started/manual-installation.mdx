For a new private-LAN installation, follow the [Builder guide](/getting-started/installation/). For a generated stack, use the project-specific commands in `INSTALLATION.txt` and the [operations and recovery guide](/guides/operations/). Do not combine a generated installation's `.env`, project identity or volumes with the repository's reference Compose file.

## Repository reference stack

`docker-compose.local.yml` is the manually maintained reference stack at the source root. It is a separate workflow: it uses fixed container names, includes both audio classifiers, and has its own configuration mounts and host-port choices. Merely changing its Compose project name does not eliminate fixed-name collisions. It is not the installer-generated single-port/selected-capability contract, and its defaults are not a verified fresh-install recipe.

<Aside type="caution">
Operate the reference stack only after reviewing its complete current configuration. Do not run these examples against an existing installation as a repair shortcut. Keep developer `docker-compose.dev.yml` / `run-dev.sh` usage in the [development guide](/guides/set-up-development-environment/).
</Aside>

The current source files are the authority. Copy values from the templates shipped with your checkout, rather than an old documentation snapshot:

| Source asset | Manual responsibility |
| --- | --- |
| `.env.template` | Create a protected `.env`; supply database, admin, broker/worker, exporter, JWT, CSRF and Grafana values. Keep established service credentials unchanged. |
| `garage.template.toml` | Create `garage.local.toml` with matching RPC/admin/metrics secrets, paths and layout configuration. |
| `rabbitmq/rabbitmq.template.conf` and `rabbitmq/definitions.template.json` | Supply the mounted broker configuration and verify each actual worker identity, vhost and queue. |
| API/worker `appsettings.Template.json` files | Supply any configuration the actual host needs that is not explicitly bound in Compose. The templates are examples, not automatically loaded runtime defaults. |
| `nginx/nginx.conf` and `nginx/certs/` | Supply the proxy's expected certificate/key names and a valid certificate for the exact chosen public host/IP. Establish client trust separately. |
| `Frontend/Dockerfile`, `.env` and Compose build arguments | Review API origin, browser crypto settings and UI feature flags before building. Frontend settings are build-time inputs. |
| `classificators/essentia/model-requirements.tsv` and model checksums | Supply every model asset required by the classifiers you actually include. The reference includes both; Builder selects at most one. |

Use one coherent HTTPS origin for browser access, CORS, public storage URLs and proxy routing. Review all `ports:` entries yourself; reference Compose does not gain the installer's one-port boundary by copying its `.env`. A stable LAN address and a trusted matching certificate are required for browser cryptography. Do not bypass certificate warnings.

## Explicit reference commands

The following Bash helper targets the **reference** stack. Replace the absolute source path and review the project name before use. It is intentionally distinct from the generated-installation helper in the operations guide.

```bash
alexandria_reference_source='/srv/Alexandria source'
alexandria_reference_project='alexandria-local'

alexandria_reference_compose() {
  docker compose \
    --project-name "$alexandria_reference_project" \
    --project-directory "$alexandria_reference_source" \
    --env-file "$alexandria_reference_source/.env" \
    --file "$alexandria_reference_source/docker-compose.local.yml" "$@"
}

alexandria_reference_compose config --quiet
```

Validation catches Compose syntax and required substitutions; it cannot prove that credentials, application settings, models or client trust are correct. Do not print fully resolved configuration: it contains secrets. Initial source builds can require registry and dependency-repository access.

For an operator who has completed the manual configuration, the bootstrap order is:

1. Build the reviewed reference services with `alexandria_reference_compose build`. Resolve build errors using build output before looking for container logs.
2. Start database, storage and messaging with `alexandria_reference_compose up -d postgres garage rabbitmq-config rabbitmq`. Check their status and readiness with `ps --all` and targeted service logs.
3. Run the storage setup job with `alexandria_reference_compose up -d --no-deps garage-init`. Wait for successful exit before starting consumers. Review the protected `init-output/garage-credentials.env` handoff locally and persist **all** generated application, preview-worker and transpilation-worker key pairs in the matching `.env`. Do not expose them in logs or support messages. Manual operators own this merge; Builder automates and verifies it for generated installations.
4. Only after complete credentials and configuration are available, use `alexandria_reference_compose up -d --no-build` for the reviewed stack. If a consumer had already started with placeholder keys, recreate that affected service with its corrected environment; a process restart alone does not update container environment values.
5. Check every included service, database/admin bootstrap, exact HTTPS origin and browser sign-in. Then perform the [client and file checks](/getting-started/first-steps/), adapting file locations to your reference configuration.

Keep the reference stack's existing settings and volume identities for subsequent starts. Do not rotate database, Garage or broker credentials to fix a readiness error. Consult [consistent backups and recovery](/guides/operations/) before modifying established state; use the reference helper and its actual volume names for this workflow.
